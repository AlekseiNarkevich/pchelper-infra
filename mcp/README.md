# MCP-сервер PCHelper

**Model Context Protocol сервер** интернет-магазина компьютерных комплектующих
**PCHelper**. Позволяет AI-ассистенту (LLM) работать с каталогом, конфигуратором,
корзиной и заказами магазина через три стандартных примитива MCP:
**Tools** (действия), **Resources** (данные) и **Prompts** (шаблоны сценариев).

> Лабораторная работа № 4, задание 5 «Проектирование MCP-сервера».

---

## 1. Зачем нужен сервер

Агентный сценарий, который закрывает сервер:

> *«Собери мне игровой ПК до 4000 BYN»* → LLM читает каталог и правила
> совместимости, подбирает комплектующие, проверяет совместимость,
> добавляет их в корзину и оформляет заказ. Затем на вопрос
> *«где мой заказ?»* — читает ресурс с последними заказами и отвечает,
> опираясь на реальные трек-номера.

Три примитива MCP:

| Примитив | Назначение | Пример |
|----------|------------|--------|
| **Tools** | Действия, изменяющие состояние | `check_compatibility`, `create_order`, `cancel_order` |
| **Resources** | Данные, доступные только для чтения | `pchelper://orders/recent`, `pchelper://compatibility/rules` |
| **Prompts** | Шаблоны сообщений для типовых сценариев | `assemble_pc`, `order_refund` |

## 2. Быстрый старт

```bash
cd mcp

# 1. Виртуальное окружение
python -m venv .venv
# Windows:
.venv\Scripts\activate
# Linux / macOS:
source .venv/bin/activate

# 2. Зависимости
pip install -r requirements.txt

# 3. Создать mock-базу и запустить сервер (stdio)
python server.py --reset

# либо запуск через Streamable HTTP (для MCP Inspector)
python server.py --http --port 8080
```

При первом запуске рядом появится файл `pchelper_mcp.db` (SQLite) —
он создаётся из `schema.sql` и наполняется данными из `seed.sql`.

### Проверка через MCP Inspector

```bash
npx @modelcontextprotocol/inspector
```

В открывшемся окне выберите транспорт **Streamable HTTP** и адрес
`http://127.0.0.1:8080/mcp`, затем нажмите **Connect**
(сервер для этого должен быть запущен с ключом `--http`).

Вкладки Inspector:

* **Tools** — список всех 13 инструментов, можно вызвать каждый и увидеть ответ;
* **Resources** — чтение всех 9 ресурсов (5 статических + 4 шаблонных);
* **Prompts** — получение шаблонов промптов с аргументами.

### Подключение к Claude Desktop

Файл `claude_desktop_config.json`:

```json
{
  "mcpServers": {
    "pchelper": {
      "command": "python",
      "args": ["C:/путь/к/проекту/mcp/server.py", "--reset"],
      "env": {
        "PCHELPER_AGENT_NAME": "claude-desktop"
      }
    }
  }
}
```

Для Cursor — аналогично, в `.cursor/mcp.json`.

## 3. Архитектура

```
Клиент (Claude Desktop / Cursor / Inspector / чат-бот)
        │  stdio  |  Streamable HTTP
        ▼
┌───────────────────────────────────────────────┐
│  MCP-сервер PCHelper (Python 3.12, FastMCP)   │
│                                               │
│  Tools (14) · Resources (9) · Prompts (5)     │
│  ─────────────────────────────────────────    │
│  audit.py — журнал действий агента + маскиров.│
│  services.py — доменная логика (без MCP)      │
│  db.py — доступ к данным                      │
└───────────────────────────────────────────────┘
        │
        ▼
   SQLite  pchelper_mcp.db
   (имена таблиц совпадают с физической моделью PostgreSQL)
```

Ключевое проектное решение: **доменная логика вынесена в `services.py` и не зависит
от MCP**. Её можно покрыть обычными юнит-тестами (`pytest`), а MCP-слой
(`server.py`) остаётся тонкой оболочкой, отвечающей за регистрацию примитивов.

JSON-схемы входных данных генерируются из типизированных сигнатур Python
(принцип типизации из документации MCP Python SDK).

### Гостевые (без авторизации)

| Инструмент | Ключевые аргументы | Результат |
|------------|--------------------|-----------|
| `search_components` | `component_type?`, `brand?`, `query?`, `min_price?`, `max_price?`, `sort`, `limit` | список товаров |
| `get_component` | `component_type`, `component_id` | карточка товара |
| `check_compatibility` | `cpu_id`, `motherboard_id`, `ram_id`, `cooling_id?`, `gpu_id?`, `storage_ids?`, `psu_id?`, `case_id?` | `{compatible, errors, warnings, totalPrice}` |
| `recommend_psu` | `cpu_id`, `gpu_id?`, `headroom=1.25` | `{recommendedWatts, alternatives}` |

### Покупательские

| Инструмент | Ключевые аргументы | Результат |
|------------|--------------------|-----------|
| `get_cart` | `user_id` | корзина |

| `apply_promo_code` | `user_id`, `code` | размер скидки |
| `create_order` | `user_id`, `phone`, `delivery_method`, `payment_method`, `address?`, `promo_code?` | заказ (статус «Новый») |
| `list_orders` | `user_id?`, `status?`, `limit` | список заказов |
| `track_order` | `order_id`, **`tracking_number`** | статус доставки |
| `cancel_order` | `order_id`, `reason`, `user_id?` | заказ со статусом «Отменён» |

| Инструмент | Ключевые аргументы | Результат |

| `set_order_status` | `order_id`, `status`, `comment?` | обновлённый заказ |

## 8. Валидация и безопасность

### 8.1. Нельзя отменить доставленный заказ

Требование задания: *«агент не должен иметь возможности отменить уже доставленный заказ»*.

Реализовано тремя независимыми уровнями защиты:

1. **`services.cancel_order`** — проверяет статус по списку
   `CANCELLABLE_STATUSES = («Новый», «В обработке»)`. При попытке отмены
   возвращается ошибка с пояснением и запись в журнал аудита с `успешно = 0`.
2. **Справочник `ПереходыСтатусовЗаказа`** — общая таблица разрешённых
   переходов, используется также инструментом `set_order_status`.
3. **В REST-API** — аналогичная проверка в `OrderService` + триггер БД
   `trg_order_cancel_guard` (`db/03_indexes_constraints.sql`),
   который возвращает ошибку даже при прямом `UPDATE` в базе.

Ни один аргумент инструмента не позволяет обойти это ограничение.

### 8.2. Инструмент `track_order` требует строгий `tracking_number`

Аргумент обязателен и должен **точно совпадать** с трек-номером в БД.
Это вынуждает LLM выполнить именно тот порядок действий, который описан
в задании: прочитать ресурс `pchelper://orders/recent` и взять значение оттуда.
Если передан неверный номер, сервер отвечает:

> *«Трек-номер не совпадает с данными заказа PCH-2026-000003. Прочитайте
> ресурс pchelper://orders/recent и используйте точное значение трек-номера из него.»*

### 8.3. Логирование действий агента

Каждый вызов инструмента и каждое чтение ресурса записываются в
`ЖурналДействийАгента`: время, идентификатор агента, имя примитива,
аргументы, результат, код ответа, признак успеха, длительность.
Персональные данные (телефон, e-mail, адрес) **маскируются** перед записью
(`audit.mask_pii`).

## 9. Примеры запросов от лица пользователя

### Сценарий А — подбор ПК под бюджет

```
Пользователь: Собери игровой ПК до 4000 BYN
LLM:          [prompts.assemble_pc(4000, "Игры")]
              [resources/read pchelper://compatibility/rules]
              [resources/read pchelper://catalog/cpu]
              [tools/call search_components(component_type="gpu", max_price=1500)]
              [tools/call check_compatibility(cpu_id=1, motherboard_id=1, ram_id=1,
                                             cooling_id=1, gpu_id=1,
                                             storage_ids=[1], psu_id=1, case_id=1)]
LLM:          Собрал: Ryzen 5 7500F + B650M-P + 16 ГБ DDR5 + RX 7700 XT …
              Итого 3 780 BYN, запас бюджета 220 BYN.
```

### Сценарий Б — отслеживание заказа

```
Пользователь: Где мой заказ?
LLM:          [resources/read pchelper://orders/recent]
              → PCH-2026-000003, статус «Отправлен», tracking_number BY-7744123
              [tools/call track_order(order_id=3, tracking_number="BY-7744123")]
LLM:          Заказ PCH-2026-000003 в пути, трек-номер BY-7744123.
```

### Сценарий В — попытка отмены (ожидается отказ)

```
Пользователь: Отмени заказ PCH-2026-000003
LLM:          [tools/call cancel_order(order_id=3, reason="передумал")]
              → isError: «Отмена невозможна: заказ PCH-2026-000003 в статусе
                 «Отправлен». Отменять можно только заказы в статусе «Новый»,
                 «В обработке». После передачи в доставку возврат оформляется
                 через службу поддержки.»
LLM:          Отменить нельзя — заказ уже отправлен. Могу оформить возврат
              через поддержку (15 % комиссия по правилам возврата).
```

### Сценарий Г — расчёт возврата

```
Пользователь: Сколько мне вернут за заказ 1042?
LLM:          [prompts.order_refund(1042)]
              [resources/read pchelper://policies/refund]     ← сначала правила
              [resources/read pchelper://orders/recent]
LLM:          Заказ в статусе «Отправлен»: возврат оформляется через поддержку,
              сумма = цена × количество − 15 % комиссии.
```

## 10. Тестирование

```bash
pytest -q
```

Ожидаемый результат: **39 тестов пройдено**.

Покрываются: каталог и фильтры, все 8 правил совместимости, расчёт БП,
корзина (включая слияние позиций и проверку остатков), промокоды,
оформление заказа со снимком цен, статусная машина (включая запрет
недопустимых переходов), запрет отмены отправленного и доставленного заказа,
строгая проверка `tracking_number`, склад, аудит и маскирование PII.

Дополнительно — ручная проверка через **MCP Inspector**: вызвать
`check_compatibility` с заведомо несовместимой сборкой (например,
`cpu_id=1` и `motherboard_id=3` — разные сокеты) и убедиться, что в ответе
`compatible: false` и присутствует ошибка `SOCKET_MISMATCH`.

## 13. Развитие (прод-режим)

Текущая реализация — MVP с mock-базой SQLite, как и требует задание.
Следующие шаги:

1. Заменить `db.get_conn()` на пул соединений к PostgreSQL
   (те же имена таблиц, `db/01…05.sql`).
2. Добавить HTTP-клиент к `api.pchelper.by` для прод-режима —
   сервисы `services.py` остаются без изменений, меняется только слой `db.py`.
3. Аутентификация агента: передавать токен в заголовке, проверять роль
   (`customer` / `manager`) в `RoleGuard`.
