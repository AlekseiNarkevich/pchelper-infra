### 0.1. Как получить изображения диаграмм

> **Все 14 диаграмм уже отрендерены** в папке `diagrams/plantuml/png/`
> и вставлены в отчёт как готовые изображения. Исходники `.puml` лежат
> рядом — если понадобится что-то поправить, перерисовать диаграмму
> можно тремя способами.

**Способ 1 — расширение VS Code (самый быстрый)**

1. Установить расширение *PlantUML Server* (jebbs) или *PlantUML* (creator.bluebear).
2. Открыть нужный файл из `diagrams/plantuml/`.
3. Нажать `Alt+D` (PlantUML Server) или кнопку «Preview» — появится панель с картинкой.
4. Правый клик по картинке → **Save Image As…** → сохранить в `diagrams/plantuml/png/`.
5. Открыть PNG и сделать скриншот (`Win + Shift + S`) — это и будет вставляться в отчёт.

**Способ 2 — онлайн-сервер**

1. Открыть https://www.plantuml.com/plantuml/umltool или https://www.plantuml.com/plantuml/text.
2. Вставить содержимое `.puml` файла.
3. Нажать **Submit** → откроется сгенерированное изображение.
4. Правый клик по картинке → **Save image as…**.

**Способ 3 — локальный plantuml.jar**

```bash
# скачать один раз
curl -L -o plantuml.jar https://github.com/plantuml/plantuml/releases/latest/download/plantuml.jar

# отрендерить все диаграммы раздела
java -jar plantuml.jar -tpng -o png diagrams/plantuml/*.puml
```

После этого в `diagrams/plantuml/png/` появятся PNG-файлы с именами диаграмм.

> **Важно про качество скриншотов.** Диаграмма должна быть читаемой на странице A4.
> Если текст мелкий — увеличь масштаб перед экспортом (в VS Code: `Ctrl + плюс`),
> либо экспортируй в SVG и вставляй в документ как векторное изображение.
> Оптимально: ширина картинки 1400–1800 px.

## 1. Задание 1. Проектирование модели требований и реестра вариантов использования

### 1.1. Исходные данные: анализ требований лабораторной работы 3

Входные данные лабораторной работы № 4 — результаты лабораторной работы № 3
(`ЛР3/LAb3.md`): 5 User Stories с критериями приёмки, базовые UML-диаграммы,
C4-модель, Event Storming и Event Modeling.

Проблема, выявленная при анализе: требования ЛР3 описывали **функциональность
пользовательского интерфейса**, но почти не описывали **договор между
клиентом и сервером**. Задание 1 требует дополнить требования так, чтобы
они **покрывали функциональность API**, а значит — довести их до уровня,
на котором по ним можно спроектировать REST API без дополнительных вопросов
к заказчику.

| Действующее лицо | Тип | Описание |
|------------------|-----|----------|

**«Покупатель»**, поскольку API различает их только уровнем аутентификации
(FR-08), а не набором функций: неавторизованный пользователь может выполнять
ровно те же операции каталога и конфигуратора.

## 2. Задание 2. Проектирование физической модели базы данных

### 2.1. Уточнение логической модели

Логическая модель, созданная в лабораторной работе 3
(`ЛР3/diagrams/plantuml/21-erd.puml`),
описывала интернет-магазин в обобщённом виде: одна таблица `Товары` с полем
`категория_id`. Для PCHelper такая модель **непригодна**, и вот почему:

1. **Гетерогенность характеристик.** Процессор имеет сокет и TDP, видеокарта —
   длину в миллиметрах и толщину в слотах, блок питания — мощность и набор
   разъёмов. Описание через общую таблицу `Товары` либо раздувает её до
   60–70 колонок с массой `NULL`, либо прячет всё в JSON без возможности
   фильтровать.
2. **Правила совместимости.** Проверка «сокет процессора = сокет платы»
   невозможна без типизированных колонок `сокет`. В обобщённой модели
   пришлось бы хранить всё в JSON и фильтровать на стороне приложения,
   что нельзя сделать индексом.
3. **Уже есть рабочая модель.** Приложение PCHelper, доставшееся в курсовой
   работе с 3 курса, использует 8 специализированных таблиц с кириллическими
   именами (`Процессоры`, `МатеринскиеПлаты`, …) и проверенную логику
   проверки совместимости. Заменять работающую модель абстрактной — ухудшение.

Поэтому за основу взята существующая модель каталога, а к ней достроены
рыночные сущности: пользователи, корзина, заказы, сохранённые сборки,
отзывы, промокоды, складские остатки и журнал действий агента.

### 2.4. Ключевые проектные решения

#### 2.4.1. Почему состав позиции хранится восемью ссылками, а не одним полем «тип + id»

Наивный вариант — хранить пару `(тип_компонента, идентификатор_компонента)`.
Он компактнее, но **не обеспечивает ссылочную целостность**: база данных
не может проверить, что видеокарта с `id = 17` действительно существует
в таблице `Видеокарты`. При удалении товара останется «висячая» ссылка.

Выбран подход восьми nullable-колонок со ссылками на восемь таблиц —
он уже применён в проекте для `ГотовыеКонфигурации`, поэтому решение
согласовано с существующим кодом. Ограничение «заполнено ровно одно поле»
закреплено CHECK-констрейнтом:

```sql
CONSTRAINT chk_single_cart_component CHECK (
    (CASE WHEN процессор_id         IS NOT NULL THEN 1 ELSE 0 END) +
    (CASE WHEN материнская_плата_id IS NOT NULL THEN 1 ELSE 0 END) +
    … всего 8 слагаемых …
) = 1
```

#### 2.4.2. Почему цена позиции заказа — это снимок

В таблице `Заказ_Позиции` хранятся `название` и `цена_за_единицу`,
зафиксированные в момент оформления. Без этого снимка изменение цены
в каталоге задним числом переписало бы историю заказов: покупатель,
оплативший 1299 BYN, увидел бы в своём заказе новую цену 1599 BYN,
а финансовый отчёт перестал бы сходиться.

Цена **готовой конфигурации**, наоборот, не хранится вовсе — она
вычисляется представлением `v_готовые_конфигурации` как сумма цен
компонентов. Это избавляет от рассинхронизации.

#### 2.4.3. Статусная машина заказа в базе данных

Разрешённые переходы вынесены в справочную таблицу
`ПереходыСтатузовЗаказа(из_status, в_status, роль_кто)`:

| Из | В | Кто может |
|----|---|-----------|
| Новый | В обработке | менеджер |
| Новый | Отменён | покупатель |
| В обработке | Собран | менеджер |
| В обработке | Отменён | покупатель |
| Собран | Отправлен | менеджер |
| Отправлен | Доставлен | менеджер |

Один справочник используют три компонента: REST-сервис `OrderService`,
MCP-инструмент `set_order_status` и триггер БД `trg_order_cancel_guard`.
Изменение правил отмены требует правки одной таблицы, а не трёх мест в коде.

#### 2.4.4. Триггер, защищающий от отмены отправленного заказа

```sql
CREATE OR REPLACE FUNCTION fn_order_cancel_guard() RETURNS trigger AS $$
BEGIN
    IF NEW.статус = 'Отменён' AND OLD.статус IN ('Собран','Отправлен','Доставлен') THEN
        RAISE EXCEPTION 'Недопустимый переход: заказ №% в статусе "%" нельзя отменить',
            OLD.номер, OLD.статус USING ERRCODE = 'check_violation';
    END IF;
    NEW.обновлён_в = now();
    RETURN NEW;
END; $$ LANGUAGE plpgsql;
```

Даже прямой `UPDATE "Заказы" SET статус = 'Отменён'` в консоли БД будет
отклонён. Это последний рубеж: правило продублировано в сервисе заказов
и в MCP-инструменте `cancel_order`.

#### 2.4.5. Типы данных под требования предметной области

| Решение | Обоснование |
|---------|-------------|
| `CITEXT` для e-mail | Регистронезависимость: `Anna@.by` и `anna@by` — один пользователь |
| `JSONB` для составных характеристик | `ядра_потоки`, `частота`, `скорость_чтения_записи` — объекты с фиксированной структурой; JSONB даёт проверку структуры через CHECK и GIN-индексы, но не раздувает таблицу |
| ENUM-типы для справочников | `component_type`, `user_role`, `order_status` — закрытые множества значений; ENUM защищает от опечаток лучше, чем `VARCHAR` + словарь |
| `NUMERIC(2,1)` для толщины видеокарты | Значение вида 2.5 слота — `NUMERIC`, а не `INTEGER` |
| Целочисленный `INTEGER` для денег | BYN без копеек; `NUMERIC` избыточен, `FLOAT` недопустим для денег |

#### 2.5.1. Представление `v_каталог` — решение проблемы гетерогенности

Восемь таблиц каталога объединены в единое представление с общим набором
колонок, а специфичные характеристики собраны в JSONB:

```sql
CREATE OR REPLACE VIEW v_каталог AS
    SELECT 'cpu'::component_type AS тип, id, название, производитель,
           цена, фото_url, tdp,
           jsonb_build_object('сокет', сокет, 'ядра', ядра_потоки -> 'cores',
                              'потоки', ядра_потоки -> 'threads', …) AS характеристики,
           создан_в
      FROM "Процессоры"
UNION ALL
    SELECT 'motherboard', id, название, NULL, цена, фото_url, NULL,
           jsonb_build_object('сокет', сокет, 'тип_памяти', тип_памяти, …), создан_в
      FROM "МатеринскиеПлаты"
UNION ALL …
```

Это позволяет отдавать каталог одной конечной точкой
`GET /catalog/components?type=gpu` и при этом сохранить специализацию
внутри модели. Разворачивание вложенного JSONB в плоские ключи
(«ядра», «потоки», «турбо_частота») выполняется в сервисе, чтобы
клиенту не приходилось знать структуру хранения.

#### 2.5.2. Функция `fn_check_compatibility` — 8 правил в базе

Все правила проверки совместимости реализованы **один раз** в PL/pgSQL-функции
и доступны как из REST-сервиса, так и для прямых запросов:

```sql
SELECT * FROM fn_check_compatibility(1, 2, 4, 3, 5, ARRAY[7]::int[], 6, 8);
-- уровень  | код                    | сообщение
-- error    | PSU_INSUFFICIENT       | Требуется минимум 794 Вт …
-- warning  | PSU_LOW_HEADROOM       | Запас мощности БП менее 15 %
```

Правила (названия кодов совпадают с кодами в MCP-сервере и в OpenAPI):

1. `SOCKET_MISMATCH` — сокет процессора и платы;
2. `MEMORY_TYPE_MISMATCH` — тип памяти;
3. `FORM_FACTOR_MISMATCH` — иерархия форм-факторов;
4. `GPU_TOO_LONG` — длина видеокарты;
5. `COOLER_TDP_TOO_LOW` — тепловая мощность охлаждения;
6. `COOLER_TOO_TALL` / `RADIATOR_TOO_LONG` — габариты охлаждения;
7. `PSU_INSUFFICIENT` / `PSU_LOW_HEADROOM` — запас мощности 25 %;
8. `SSD_COUNT` / `HDD_COUNT` — состав накопителей.

### 3.1. Соглашения по проектированию

| Соглашение | Правило | Обоснование |
|-----------|---------|-------------|
| Версионирование | Префикс пути `/api/v1` | Позволяет выпустить несовместимое изменение как `/api/v2`, не ломая клиентов |
| Имена ресурсов | **Множественное число**, строчные буквы, через дефис | `catalog/components`, `orders`, `admin/analytics/sales` — по рекомендациям GetAnalyst |
| Вложенность | Максимум два уровня после корня | `/admin/orders/{id}/status` допустимо; `/a/b/c/d/e` — признак плохой модели |
| Действия над коллекцией | `POST` на коллекцию — создание | `POST /orders` создаёт заказ |
| Действие над элементом | `POST` на `/элемент/действие` — глагол-действие | `POST /orders/{id}/cancel` — не `PUT /orders/{id}`, потому что отмена — это переход состояния, а не замена полей |
| Частичное обновление | `PATCH`, полная замена — `PUT` | `PATCH /cart/items/{id}` меняет только количество |
| Удаление | `DELETE` + код `204` | Тело ответа отсутствует |
| Идентификаторы | `integer`, в пути `{camelCase}` | `{componentId}`, `{orderId}`, `{buildId}` |
| Даты | ISO 8601 в UTC | `2026-10-13T09:15:00Z` |
| Деньги | Целые числа, BYN | Без плавающей точки — исключены ошибки округления |
| Пагинация | `page` (с 1) + `limit` (по умолчанию 20, максимум 100) | Совместимо с NFR-01 (отклик < 500 мс) |
| Фильтрация | Параметры запроса с префиксом имени поля | `?type=gpu&minPrice=500&maxPrice=2000&sort=price_asc` |
| Ошибки | Единый конверт `{ "error": { "code", "message", "details" } }` | Машиночитаемый `code` для клиента и текстовое `message` для пользователя (NFR-09) |

### 3.5. Значение HTTP-статусов в проекте

| Код | Значение в PCHelper | Когда используется |
|-----|--------------------|--------------------|
| 200 OK | Успех, тело содержит результат | Чтение, обновление, действия |
| 201 Created | Создан новый ресурс | Регистрация, добавление в корзину, оформление заказа, создание сборки |
| 204 No Content | Успех, тело отсутствует | Удаление позиции, удаление сборки, снятие товара с продажи |
| 400 Bad Request | Запрос синтаксически или логически неполон | Нет обязательного поля, `quantity` вне диапазона 1…10, перепутаны `количество` и `delta` |
| 401 Unauthorized | Нет токена либо он истёк | Защищённая конечная точка без `Authorization` |
| 403 Forbidden | Токен есть, но не та роль | Покупатель обращается к `/admin`, читает чужой заказ |
| 404 Not Found | Ресурс не найден | Несуществующий `componentId`, `orderId`, `symptomId` |
| 409 Conflict | Конфликт с текущим состоянием | Повторная регистрация e-mail, нехватка товара, отмена отправленного заказа, недопустимый переход статуса |
| 422 Unprocessable Entity | Запрос корректен, но семантически невыполним | Компонент не найден по переданному идентификатору, несовместимая сборка в заказе |
| 500 Internal Server Error | Непредвиденная ошибка | Сбой БД, необработанное исключение |
| 503 Service Unavailable | Зависимость недоступна | БД или кэш не отвечают |

### 3.7. Открытая спецификация и интерактивная документация

1. Спецификация `api/openapi.yaml` хранится рядом с кодом лабораторной
   работы и проверяется линтером Redocly на каждом запуске конвейера.
2. Из того же файла собирается интерактивная документация Redoc, где
   каждая операция раскрывается с примерами запроса, примерами ответа,
   схемами и перечнем кодов ответа:

   ```bash
   npx @redocly/cli build-docs api/openapi.yaml --output api/dist/index.html
   ```

   Эту же команду выполняет конвейер на этапе «Генерация Swagger»
   (раздел 6.8.2); собранные файлы складываются в артефакт
   `swagger-docs` прогона.
3. Собранная страница намеренно **не коммитится в репозиторий**: это
   результат сборки, а не исходный код. Ветка с файлом на 640 КБ
   раздувала отчёт SonarCloud на новом коде и роняла Quality Gate,
   поэтому документация собирается по требованию, а хранится как
   артефакт прогона.
4. Backend намеренно не занимается документацией: в этом учебном стенде
   он минимальное приложение «Hello World», нужное только для проверки
   работоспособности окружения. Код магазина в стенд не переносился, а
   документация к нему публикуется из спецификации — так она не может
   разойтись с описанием API.
5. Описание ресурсов и примеры запросов продублированы в документации
   проекта — на странице вики «API-проекта» и на странице сайта
   `api.html` (раздел 4.6).

### 4.1. Выбор инструмента

Методичка предлагает три сервиса с поддержкой Open API. Сравнение:

| Критерий | SwaggerHub | Postman | Bruno |
|----------|-----------|---------|-------|
| Бесплатный тариф | Есть (ограничения на приватность) | Есть | **Полностью бесплатный, open source** |
| Mock-сервер | Встроенный, автоматически создаётся из спецификации | Есть (Mock-сервер на основе коллекции) | **Встроенный, запуск в один клик** |
| Импорт Open API | `YAML → Import API` | `Import → Link` | `Import → OpenAPI` |
| Генерация клиентского кода | Да (OpenAPI Generator) | Ограниченно | Нет |
| Генерация документации | Да | Да (HTML) | **Да (docs из спецификации)** |
| Локальный запуск | Нет | Нет | **Да, офлайн** |
| Интеграция с Git | Платно | Платно | **Бесплатно, файл в репозитории** |
| Формат хранения | Платный сервис | Платный сервис | **Обычные текстовые файлы (.bru) в репозитории** |

**Выбор — Bruno**, по трём причинам:

1. Коллекция запросов хранится обычными файлами `.bru` в репозитории —
   она проходит ревью вместе с кодом и не теряется при смене аккаунта;
2. Встроенный Mock-сервер запускается одной командой и не требует
   платного тарифа;
3. Bruno умеет сгенерировать документацию API прямо из спецификации

### 4.2. Создание API в сервисе

Порядок действий для Bruno (аналогичные шаги для SwaggerHub и Postman):

1. Установить Bruno: <https://docs.usebruno.com/get-started/installation>.

   коллекция лежит на диске в виде обычных файлов и никуда не отправляется.
2. На стартовом экране выбрать **Import from OpenAPI** и указать файл
   `api/openapi.yaml`. В диалоге импорта оставить формат
   **OpenCollection (YAML)** и разбивку **по тегам** — тогда Bruno

   изменения спецификации, которых здесь нет.
   Готовая коллекция из той же спецификации лежит в репозитории —
   `bruno/pchelper-collection.json`.
3. Приложить спецификацию к коллекции: **API Specs → +** → тот же
   `api/openapi.yaml`. По ней Bruno строит mock-сервер.
4. Выбрать окружение **Локальная разработка (Docker Compose)**:

| Переменная | Значение |
|-----------|----------|
| `baseUrl` | `http://localhost:3001/api/v1` |
| `accessToken` | заполняется автоматически скриптом из ответа `login` |
| `refreshToken` | заполняется автоматически |
| `componentId`, `orderId`, `buildId`, `configId` | подставляются в тесты |

5. Создать сервер: **Mock Servers → +**, имя `PCHelper`, источник —

**Как читать графу «Фактически».** Mock-сервер Bruno не выполняет
бизнес-логику приложения: он подставляет готовые примеры ответов из
спецификации `api/openapi.yaml`. Поэтому фактический код внутри тела
может отличаться от того, который ожидался по постановке задачи, —
пример для TC-08 спецификация отдаёт ошибку `PSU_INSUFFICIENT`, а не
`socket`. Проверяется класс ответа (200 / 4xx) и наличие ожидаемых
полей в теле, а не конкретный код ошибки внутри. Там, где спецификация
описывает несколько вариантов ответа для одной операции, Bruno создаёт
по mock-ответу на каждый код, и нужный выбирается вручную — так был
получен ответ 403 в TC-33.

Ключевыми для проверки бизнес-логики являются TC-27 (запрет отмены
отправленного заказа), TC-32 (недопустимый переход статуса),
TC-24 (фиксация снимка цен) и TC-08 (проверка совместимости).

#### 5.4.1. Решение: два транспорта

| Транспорт | Когда используется | Как запустить |
|-----------|--------------------|---------------|
| **stdio** | Claude Desktop, Cursor — сервер запускается как дочерний процесс клиента | `python server.py` |

Один и тот же код обслуживает оба транспорта — переключение флагом `--http`
в функции `main` (4 строки, `mcp/server.py`).

#### 5.4.2. Решение: доменная логика отделена от MCP

```
server.py    ← тонкий слой: регистрация примитивов, вызов services.py
services.py  ← доменная логика, НЕ импортирует mcp
audit.py     ← аудит, не зависит ни от mcp, ни от домена
db.py        ← доступ к данным
```

**Обоснование:** доменную логику можно покрыть обычными юнит-тестами `pytest`
**без установки пакета `mcp`**. CI запускает эти тесты за секунды. Если бы
логика жила внутри декораторов `@mcp.tool()`, тестировать её пришлось бы
через протокол, что в разы медленнее и хрупче.

#### 5.5.1. Принципы типизации аргументов

Инструменты типизированы по правилам MCP Python SDK:

### 5.8. Валидация бизнес-правил

#### 5.8.1. Запрет отмены доставленного заказа

**Требование:** *«Необходимо реализовать валидацию (агент не должен иметь
возможности отменить уже доставленный заказ)».*

```python
CANCELLABLE_STATUSES = ("Новый", "В обработке")

def cancel_order(order_id: int, reason: str, user_id: int | None = None) -> dict:
    with get_conn() as conn:
        order = _fetch_one(conn, 'SELECT * FROM "Заказы" WHERE id = ?', (order_id,))
        if not order:
            raise BusinessError(f"Заказ {order_id} не найден.")
        if user_id is not None and order["пользователь_id"] != user_id:
            raise BusinessError("Заказ принадлежит другому пользователю.")

        current = order["статус"]
        if current not in CANCELLABLE_STATUSES:
            conn.execute(
                'INSERT INTO "ЖурналДействийАгента" '
                "(агент, инструмент, аргументы, результат, код_ответа, успешно) "
                "VALUES (?, ?, ?, ?, ?, 0)",
                ("mcp-server", "cancel_order", ...,
                 f"Отказ: статус «{current}» не допускает отмены", 409))
            conn.commit()
            raise BusinessError(
                f"Отмена невозможна: заказ {order['номер']} в статусе «{current}». "
                f"Отменять можно только заказы в статусе «{CANCELLABLE_STATUSES}». "
                f"После передачи в доставку возврат оформляется через службу поддержки.")
```

Ни один аргумент инструмента `cancel_order` не обходит ограничение:
проверка происходит **после** чтения заказа из базы и **до** записи.
Попытка отмены **логируется как отказ** (`успешно = 0`, `код_ответа = 409`),
поэтому в журнале видно, если агент регулярно пытается отменить
доставленные заказы.

Три независимых уровня защиты перечислены в разделе 2.4.4
(справочник переходов) и продублированы в REST-API.

#### 5.8.2. Строгая проверка `tracking_number`

**Требование:** *«Tool track_package должен требовать строгого указания
tracking_number, которое LLM возьмёт из прочитанного ресурса».*

```python
def track_order(order_id: int, tracking_number: str) -> dict:
    with get_conn() as conn:
        order = _fetch_one(conn, 'SELECT * FROM "Заказы" WHERE id = ?', (order_id,))
        if not order:
            raise BusinessError(f"Заказ {order_id} не найден.")
        if not order["трек_номер"]:
            raise BusinessError(
                f"Заказ {order['номер']} ещё не передан в доставку — "
                f"трек-номен не присвоен. Текущий статус: «{order['статус']}».")
        if not tracking_number or tracking_number.strip().upper() != order["трек_номер"].upper():
            raise BusinessError(
                f"Трек-номер не совпадает с данными заказа {order['номер']}. "
                f"Прочитайте ресурс pchelper://orders/recent и используйте "
                f"точное значение трек-номера из него.")
    return {…}
```

| Вход | Результат |
|------|-----------|
| Точный трек-номер из ресурса | 200, статус доставки |
| Другой трек-номер | `isError` с указанием прочитать `pchelper://orders/recent` |
| Пустая строка | `isError` |
| Заказ ещё не отправлен | `isError`: «трек-номен не присвоен, текущий статус …» |

#### 5.8.3. Валидация входных данных

| Проверка | Место | Поведение при нарушении |
|----------|-------|------------------------|
| Тип компонента в перечне | `services._component`, `search_components` | `BusinessError` со списком допустимых значений |
| Компонент существует | `services._component` | `BusinessError` с указанием идентификатора и типа |
| `minPrice ≤ maxPrice` | `search_components` | `BusinessError`: «minPrice не может превышать maxPrice» |
| `quantity` в диапазоне 1…10 | `add_to_cart` | `BusinessError`: «Количество должно от 1 до 10» |
| Остаток на складе | `add_to_cart`, `create_order` | `BusinessError`: «Доступно N шт., запрошено M» |
| Адрес при доставке курьером | `create_order` | `BusinessError`: «требуется адрес» |
| Причина отмены непустая | `cancel_order` | `BusinessError`: «Укажите причину отмены» |
| Заказ принадлежит пользователю | `cancel_order`, `get_order` | `BusinessError`: «Заказ принадлежит другому пользователю» |
| Переход статуса разрешён | `set_order_status` | `BusinessError` со списком допустимых переходов |

### 5.9. Аудит и маскирование персональных данных

**Требование:** *«Особенность: работа с конфиденциальными данными
(требование к логированию действий агента)».*

Каждый вызов инструмента и чтение ресурса оборачиваются контекстным
менеджером `audit.audit()`:

```python
@mcp.tool()
def cancel_order(order_id: int, reason: str, user_id: int | None = None) -> dict:
    with audit.audit(AGENT, "cancel_order",
                     {"order_id": order_id, "reason": reason}) as ctx:
        order = services.cancel_order(order_id, reason, user_id)
        ctx["result"] = "Отменён"
        return order
```

| Поле журнала | Пример значения |
|--------------|----------------|
| `момент` | `2026-10-13 09:20:41` |
| `агент` | `claude-desktop` |
| `инструмент` | `cancel_order` |
| `аргументы` (JSON) | `{"orderId": 3, "reason": "передумал"}` — **PII замаскировано** |
| `результат` | `Отменён` либо `Отказ: статус «Отправлен» не допускает отмены` |
| `код_ответа` | `200` / `409` / `400` |
| `успешно` | `1` / `0` |
| `длительность_мс` | `12` |

**Маскирование PII** (`audit.mask_pii`) применяется перед записью:

| Поле | Исходное значение | В журнале |
|------|-------------------|-----------|
| `phone` | `+375291112233` | `+375…33` |
| `email` | `anna@example.by` | `an***@example.by` |
| `address` | `ул. Ленина, 15, кв. 42` | `***` |
| `orderId` | `3` | `3` — не персональные данные, не меняются |

Фактические записи журнала после прогона тестов:

```
AUDIT: {'инструмент': 'cancel_order', 'результат': 'Отменён', 'код_ответа': 200, 'успешно': 1}
AUDIT: {'инструмент': 'cancel_order', 'результат': 'Отказ: статус «Доставлен» не допускает отмены', 'код_ответа': 409, 'успешно': 0}
AUDIT: {'инструмент': 'cancel_order', 'результат': 'Отказ: статус «Отправлен» не допускает отмены', 'код_ответа': 409, 'успешно': 0}
```

Отказы зафиксированы отдельно и с кодом 409 — при разборе инцидента
будет видно, что агент пытался совершить недопустимое действие.

#### 6.1.2. Модель веток

Согласованная командой модель, одинаковая для всех репозиториев.
Фактически в `pchelper-infra` сейчас создана только ветка `main`;
остальные ветки появятся вместе с первыми задачами из GitHub Project:

| Ветка | Назначение |
|-------|-----------|
| `main` | Продакшн. Защищена: требуется approve и зелёный статус CI |
| `develop` | Интеграция, сюда сливаются feature-ветки |
| `feature/<задача>` | Одна задача из GitHub Project |
| `release/<версия>` | Подготовка релиза из `develop` |
| `hotfix/<проблема>` | Срочное исправление из `main` |

#### 6.1.3. Соглашение о ветках

| Ветка | Назначение | Правило |
|-------|-----------|---------|
| `main` | Продакшн | Защищена правилом `Protect main`: обязателен **pull request** (0 approvals — на этапе лабораторной работу ведёт один человек), **зелёный статус CI**, squash-слияние, запрет force push и удаления ветки. Только коммиты, прошедшие тесты, SonarQube Quality Gate и попавшие в собранный образ |
| `develop` | Интеграция | Все feature-ветки сливаются сюда. Здесь же прогоняется полный CI |
| `feature/<задача>` | Одна задача из Project | Ветка создаётся под **один issue**. Коммиты вида `feat(api): добавлен POST /cart/merge (#42)` |
| `release/<версия>` | Подготовка релиза | Создаётся из `develop`, в неё переносятся только исправления |
| `hotfix/<проблема>` | Срочное исправление | Из `main`, сливается и в `main`, и в `develop` |

**Обязательные правила, согласованные командой:**

1. Разработка ведётся **только через систему контроля версий** — правки
   в `main` напрямую запрещены, ветка защищена настройками GitHub.
2. Каждая задача из GitHub Project = отдельный issue с чеклистом
   критериев приёмки.
3. Pull Request обязателен; в шаблоне PR — чек-лист ревью
   (`.github/PULL_REQUEST_TEMPLATE.md`).
4. Merge в `main` только при зелёных проверках: тесты, Quality Gate,
   успешная сборка образа.
5. Сообщения коммитов — на английском в формате Conventional Commits.

![Рис. 31. Репозиторий pchelper-infra на GitHub](https://alekseinarkevich.github.io/pchelper-infra/img/shots/29-github-repo-code.png)

Правило создано с параметрами *Enforcement status: Active*, раздел
**Targets → Branches** с паттерном `main` и набором правил
*Require a pull request before merging* (0 approvals),
*Do not allow bypassing the above settings*, *Block force pushes*,
*Restrict deletions*, *Require linear history*, *Squash and merge only*,
*Require status checks to pass before merging* — проверки **Lint**,
**Тесты**, **Swagger**.

**Как настраивается (пошагово):**

1. *Settings → Rulesets → **New ruleset*** → в выпадающем списке **Branch**.
2. **Ruleset Name:** `Protect main`.
3. **Enforcement status:** `Active` (не `Disabled` и не `Evaluate`).
4. **Rules → Target branches → Include:** добавить `refs/heads/main`.
5. Включить правила:
   * **Require a pull request before merging** — Required approvals: `1`
     (см. примечание ниже);
   * **Do not allow bypassing the above settings** — чтобы правило
     нельзя было обойти кнопкой *Admin*;
   * **Block force pushes** — запрет `git push --force`;
   * **Restrict deletions** — запрет удаления ветки;
   * **Require linear history** — запрет merge-коммитов.
6. **Require status checks to pass before merging** — включить
   *после* первого прогона workflow: GitHub показывает в списке
   только те проверки, которые уже отработали хотя бы раз.
   Добавить: `lint`, `unit-and-integration`, `openapi-spec`,
   `sonar-quality-gate`, `build-and-push`.

> **Примечание про Required approvals.** Если работаешь один,
> поставь `0 approvals` — правило «Require a pull request»
> всё равно останется (коммит в `main` только через PR),
> но мержить сможешь ты сам. Если в группе есть другие участники
> и вы правда делаете код-ревью друг другу — ставь `1`.
> Значение выбирается один раз и попадает в скриншот, поэтому
> должно соответствовать реальному процессу.

> **Почему Rulesets, а не Branch protection rules.** GitHub в 2024 году
> перенёс настройки защиты веток в раздел *Rulesets* и постепенно
> убирает старый интерфейс. В новом интерфейсе появились правила,
> которых не было раньше: *Do not allow bypassing the above settings*
> и *Require linear history*. Используется именно он.

#### 6.5.2. Решения по контейнеризации

| Решение | Обоснование |
|---------|-------------|
| **Многостадийная сборка backend** (`deps` → `dev` → `prod`) | В production-образ не попадают dev-зависимости и исходники тестов; целевой слой `deps` кэшируется между сборками |
| **Запуск от непривилегированного пользователя** | В `prod`-стадии создаётся пользователь `pchelper`, `USER pchelper` — минимизация поверхности атаки |
| **`tini` как entrypoint** | Корректная обработка `SIGTERM` от Docker Compose: контейнер успевает завершить запросы |
| **Healthcheck в каждом образе** | `depends_on: condition: service_healthy` — API стартует только после готовности БД и кэша |
| **Схема БД в `/docker-entrypoint-initdb.d`** | Скрипты из `db/` применяются автоматически при первом запуске `postgres` |
| **Профили `test` и `mcp`** | Обычный запуск поднимает только 5 контейнеров; тесты и MCP — по требованию |
| **Переменные окружения в `.env`** | Секреты не попадают в образ и в репозиторий; `.env` в `.gitignore` |
| **`nginx` с SPA-fallback и проксированием `/api`** | Фронтенд работает на относительном URL `/api/v1` в любом окружении — не нужно пересобирать при смене адреса API |

#### 6.5.3. Dockerfile (backend, сокращённо)

```dockerfile
# ---------- Этап 1: только production-зависимости ----------
# Вынесено в отдельный слой, чтобы Docker кэшировал npm ci
# и не переустанавливал пакеты при каждом изменении исходников
FROM node:20-alpine AS deps
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev

# ---------- Этап 2: итоговый образ ----------
FROM node:20-alpine AS prod
WORKDIR /app

# Режим работы и порт, который слушает приложение
ENV NODE_ENV=production PORT=3001

# tini — минимальный init-процесс: корректно обрабатывает SIGTERM
# от Docker Compose, поэтому контейнер успевает завершить запросы
RUN apk add --no-cache tini

# Забираем node_modules из слоя deps (dev-зависимости туда не попали)
COPY --from=deps /app/node_modules ./node_modules
COPY package*.json ./
COPY server.js ./
COPY src ./src
COPY openapi.yaml ./openapi.yaml

# Создаём непривилегированного пользователя и передаём ему владение файлами:
# процесс внутри контейнера не должен работать от root
RUN addgroup -S pchelper && adduser -S pchelper -G pchelper \
    && chown -R pchelper:pchelper /app
USER pchelper

# Порт, который приложение слушает ВНУТРИ контейнера
EXPOSE 3001

# Проверка живости: каждые 30 секунд опрашиваем /health.
# Пока healthcheck не пройден, docker-compose не считает сервис готовым
# и не запускает зависящие от него контейнеры.
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
    CMD wget -qO- http://127.0.0.1:3001/api/v1/health || exit 1

# tini обязателен первой в ENTRYPOINT, чтобы SIGTERM дошёл до node
ENTRYPOINT ["/sbin/tini", "--"]
CMD ["node", "server.js"]
```

Оба файла приведены выше в виде листингов — они и есть доказательство.
Отдельные скриншоты не нужны.

### 6.8. CI/CD-конвейер

**Файл:** `diagrams/plantuml/11-cicd-pipeline.puml`

![Рис. 38. CI/CD-конвейер PCHelper (GitHub Actions + SonarQube + Docker + Render)](https://alekseinarkevich.github.io/pchelper-infra/img/11-cicd-pipeline.png)

#### 6.8.1. Этапы конвейера

```
pull request → develop
  ├─ 0. lint              ESLint + Prettier --check
  ├─ 1. test              unit-тесты + покрытие c8 (lcov.info)
  └─ 2. openapi           redocly lint → bundle → генерация Swagger

push → main
  ├─ 3. sonar             SonarQube Quality Gate (wait=true, таймаут 300 с)
  ├─ 4. build-and-push    сборка и публикация образов в GHCR (:latest и :sha)
  └─ 5. deploy            вебхук Render
```

**Зависимости между этапами** (объявлены через `needs`):

| Этап | Зависит от | Условие запуска |
|------|-----------|-----------------|
| `lint` | — | всегда |
| `test` | `lint` | всегда |
| `openapi` | `lint` | всегда, идёт параллельно с тестами |
| `sonar` | `test`, `lint` | только при пуше в `main` |
| `build-and-push` | `test`, `sonar` | `test` — успех **и** `sonar` — успех или пропущен |
| `deploy` | `build-and-push` | только при пуше в `main` |

Таким образом, образ публикуется только после зелёных тестов
**и** зелёного Quality Gate. Если SonarQube провалился — публикации
не будет: условие требует именно `needs.sonar.result == 'success'`.

#### 6.8.1.1. Секреты, необходимые для конвейера

*Settings → Secrets and variables → Actions → New repository secret*

| Секрет | Где получить | Что делает без него |
|--------|--------------|--------------------|
| `SONAR_TOKEN` | Личный кабинет SonarCloud: *My Account → Security → Generate Token* | Этап 3 завершается ошибкой с инструкцией — Quality Gate не выполняется, образы не собираются |
| `RENDER_DEPLOY_HOOK` | Панель Render: веб-сервис → *Settings → Deploy Hook* | Этап 5 выводит предупреждение и завершается успешно |
| `GITHUB_TOKEN` | выдаётся автоматически | Публикация образов в GHCR |

> **Важное ограничение синтаксиса GitHub Actions.** Контекст `secrets`
> **недоступен** в условии `if` на уровне задания (`jobs.<id>.if`).
> Разрешены только `github`, `needs`, `vars` и `inputs`. Если написать
> `secrets.SONAR_TOKEN != ''` в условии задания, GitHub отвергает
> **весь файл** целиком: запуск падает за 0 секунд, не создаётся ни
> одного этапа, а имя конвейера в списке заменяется именем файла.
> Поэтому проверка наличия секрета выполняется **внутри шага** —
> на уровне шага контекст `env` доступен:

```yaml
# Правильно: проверка секрета внутри шага
- name: Проверить наличие токена SonarQube
  id: token
  env:
    TOKEN: ${{ secrets.SONAR_TOKEN }}     # secrets разрешён в env
  run: |
    if [ -z "$TOKEN" ]; then
      echo "::error::Секрет SONAR_TOKEN не создан"
      exit 1
    fi

# Неправильно: secrets в условии задания -> файл не разбирается
sonar:
  if: github.ref == 'refs/heads/main' && secrets.SONAR_TOKEN != ''
```

Эта ошибка была обнаружена на практике: первый вариант конвейера
с таким условием падал за 0 секунд и не создавал ни одного этапа.

#### 6.8.2. Генерация Swagger на этапе сборки (пункт 11)

```yaml
# Задание GitHub Actions, генерирующее спецификацию Swagger.
# Выполняется параллельно с тестами: документация не должна ждать
# успешного Quality Gate, но обязана проверяться линтером.
openapi:
  name: Генерация Swagger
  steps:
    # Устанавливаем линтер спецификаций OpenAPI
    - run: npm install --global @redocly/cli

    # Шаг 1. Проверка: синтаксис, ссылки $ref, соответствие примеров схемам
    - run: redocly lint api/openapi.yaml

    # Шаг 2. Сборка всех $ref в один самодостаточный файл
    - run: redocly bundle api/openapi.yaml --output api/dist/openapi.bundled.yaml

    # Шаг 3. Статическая HTML-документация (Redoc)
    - run: npx @redocly/cli build-docs api/dist/openapi.bundled.yaml --output api/dist/index.html

    # Шаг 4. Выгрузка результата артефактом — к нему обращаются
    # при публикации документации проекта
    - uses: actions/upload-artifact@v4
      with:
        name: swagger-docs
        path: api/dist/
```

Артефакт `swagger-docs` содержит статическую страницу документации,
собранную из того же `openapi.yaml`, — спецификация API всегда
соответствует коду.

```properties

sonar.organization=students-trio

# --- Спецификация API: SonarQube умеет проверять контракт OpenAPI ---
```

#### 6.10.1. Настройка Render

1. `render.com` → **New → Web Service** → подключить репозиторий
   [`AlekseiNarkevich/pchelper-infra`](https://github.com/AlekseiNarkevich/pchelper-infra)

2. **Build Command:** Render сам выполнит `docker build` по `Dockerfile` из
   каталога `backend` — отдельная команда не нужна.
3. **Start Command:** задаётся в `Dockerfile` (`CMD ["node", "src/server.js"]`)
4. **Environment:** переменные из `.env.example`; `DATABASE_URL` указывает
   на внешний PostgreSQL (Supabase / Neon / Render PostgreSQL).
5. **Auto-Deploy: No** — деплой управляется из CI через Deploy Hook.
6. Скопировать **Deploy Hook** в секрет репозитория `RENDER_DEPLOY_HOOK`.

#### 6.10.3. Как деплой связан с конвейером

Полная цепочка проверена на коммите `5f38c26`:

```
коммит в main
   └─ конвейер: Lint → Тесты → Swagger → Quality Gate → образы
        └─ этап deploy вызывает Deploy Hook
             └─ Render пересобирает контейнер из Dockerfile
                  └─ сервис отвечает на pchelper-infra.onrender.com
```

Ключевой момент: **Auto-Deploy у Render выключен**. Иначе платформа
пересобирала бы сервис на каждом коммите, в том числе на красных
проверках, и требование «развертывать только после прохождения тестов
и проверки качества кода» было бы нарушено. Единственный путь
развёртывания — вебхук из последнего этапа конвейера, который
запускается уже после зелёного Quality Gate.

#### 6.10.4. Особенность healthcheck при развёртывании

Healthcheck в `Dockerfile` не зашивает порт, а читает переменную
окружения:

```dockerfile
HEALTHCHECK CMD wget -qO- "http://127.0.0.1:${PORT:-3001}/api/v1/health" || exit 1
```

Локально в `docker-compose` переменная `PORT` равна `3001`, поэтому
поведение не меняется. Но Render назначает контейнеру случайный порт
(в нашем случае `10000`) и передаёт его через `PORT`. С жёстко
зашитым `3001` проверка ходила бы в пустоту и помечала контейнер как
`unhealthy` — сервис не доходил бы до состояния *Live*.

В логах контейнера это видно:

```
[pchelper-api] Сервер запущен: http://0.0.0.0:10000
[pchelper-api] Режим: production
==> Your service is live
```

Сервис развёрнут и отвечает по адресу
<https://pchelper-infra.onrender.com>: проверка `GET /api/v1/health`
возвращает `200`, корневой маршрут отдаёт JSON-визитку со списком
маршрутов.

### 7.3. Дополнительная спецификация

**Ограничения**

| Ограничение | Значение |
|-------------|----------|
| Валюта | Только BYN, без конвертации и округлений |
| Язык интерфейса и API | Русский; описания ошибок и сообщения LLM — на русском |
| Рынок | Беларусь (поле НДС и коды валют не предусмотрено) |
| Роли | Только `customer` и `manager`; отдельной роли администратора нет |
| Бесплатные хостинги | Render засыпает после 15 минут простоя — первый запрос будет медленным |

**Безопасность**

| Требование | Реализация |
|-----------|-------------|
| Пароли не хранятся в открытом виде | Хеширование bcrypt, поле `password_hash` |
| Токены | JWT access (30 мин) + opaque refresh (30 дней) в БД в виде хеша |
| CORS | Явный список разрешённых источников вместо `origin: true` |
| SQL-инъекции | Только параметризованные запросы через репозитории |
| Разграничение доступа | Middleware `requireAuth` и `requireRole` на всех защищённых маршрутах |
| PII в журналах | Маскирование телефона, e-mail и адреса перед записью |
| Служебный ключ | `SUPABASE_SERVICE_ROLE_KEY` не используется в браузерном коде |

**Надёжность**

| Требование | Реализация |
|-----------|-------------|
| Отказоустойчивость БД | Транзакция при оформлении заказа: проверка остатков → резерв → позиции → очистка корзины |
| Согласованность остатков | `CHECK (зарезервировано <= количество)` в БД |
| Целостность заказов | Снимок цен и названий в `Заказ_Позиции` |
| Healthcheck | В каждом Docker-образе; `depends_on: condition: service_healthy` |
| Устойчивость к ошибкам | Единый формат ошибки `{error: {code, message}}` |

**Масштабирование**

| Направление | Текущее состояние | План |
|-----------|------------------|------|
| Каталог | Чтение через PostgREST, индексированные фильтры | Перенос на отдельный read-replica при росте трафика |
| Корзина | Хранится в PostgreSQL | Перенос в Redis с записью в БД при оформлении |
| Конфигуратор | Проверка совместимости на сервере | Кеширование результатов в Redis по хешу набора идентификаторов |
| API | Горизонтально масштабируем (stateless, кроме сессий в Redis) | — |

### 9.2. Ключевые проектные решения

| № | Решение | Альтернатива, отклонённая по причине |
|---|---------|----------------------------------------|
| 1 | Восемь специализированных таблиц каталога | Единая таблица `Товары` — невозможны проверки совместимости через индексы |
| 2 | Состав позиции — восемь nullable-FK с CHECK «ровно одно» | Пара `(тип, id)` — нет ссылочной целостности |
| 3 | Снимок цены и названия в `Заказ_Позиции` | Ссылка на текущую цену — история заказов переписывается |
| 4 | Справочник `ПереходыСтатусовЗаказа` + триггер | Проверка только в коде — обходится прямым `UPDATE` |
| 5 | Представление `v_каталog` вместо дублирования таблиц | Дублирование данных — рассинхронизация |
| 6 | `POST /orders/{id}/cancel` вместо `PUT /orders/{id}` | `PUT` означает полную замену, а отмена — это переход состояния |
| 7 | Доменная логика MCP в `services.py` без зависимости от `mcp` | Логика внутри `@mcp.tool()` — невозможно покрыть быстрыми юнит-тестами |
| 8 | `track_order` требует точного `tracking_number` | Без проверки LLM выдумывает трек-номера |
| 9 | Маскирование PII перед записью в журнал | Запись полного телефона и адреса — нарушение NFR-10 |
| 10 | Публикация образа только после Quality Gate | Публикация всегда — сборка не защищена качеством |
| 11 | Bruno вместо SwaggerHub и Postman | Коллекция `.bru` хранится в репозитории и проходит ревью |

### 9.4. Что осталось за рамками лабораторной работы

Следующие шаги развития проекта:

   соединений, имена таблиц уже совпадают.
2. **Прод-режим MCP через REST API** — те же `services.py`, меняется
   только слой доступа к данным.
3. **Мобильное приложение** — нативное Android-приложение, использует тот же
   REST API, что и веб-клиент.
4. **Интеграция с платёжным провайдером** — вебхуки и сверка статусов.
5. **Push-уведомления** — сервис-воркер на очередях Redis.
6. **Рекомендательная система** — подбор сборок на основе истории заказов.
